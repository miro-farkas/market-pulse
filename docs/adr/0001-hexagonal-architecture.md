# ADR-0001: Hexagonal architecture with build-enforced layering

- Status: Accepted
- Date: 2026-10-02

## Context
The code base is largely generated by an AI assistant. Without hard boundaries, generated code drifts:
entities leak into REST responses, Kafka types appear in business logic, frameworks spread everywhere.
The project also serves as a teaching example, so structure must be obvious.

## Decision
- Packages: `domain`, `application` (`port.in`, `port.out`, use-case services), `adapter.in.{rest,messaging}`,
  `adapter.out.{persistence,messaging,exchange}`, `config`.
- `domain` is plain Java (records, pure functions). Stream logic such as candle aggregation and alert
  evaluation lives here as pure, synchronously testable code; adapters wire it into Mutiny/Kafka.
- `application` may use Mutiny, CDI and `@WithTransaction`; no transport or persistence types.
- Adapters depend inward only; `adapter.in` never depends on `adapter.out`.
- Rules are enforced by ArchUnit (`ArchitectureTest`) in `mvn verify`, not only documented.

## Consequences
+ Domain logic is testable without Quarkus, Kafka or a database.
+ Violations fail CI, which gives the AI assistant immediate, precise feedback.
− More mapping code (entities ↔ domain ↔ DTOs/events).
− Mutiny in application ports couples use cases to Mutiny; accepted because reactive is the point (ADR-0002).

## Alternatives considered
- Layered by technical type (controller/service/repository): weaker boundaries, harder to enforce.
- Fully framework-free application layer (CompletionStage/Flow.Publisher): purer but noisy; no benefit for a demo.
